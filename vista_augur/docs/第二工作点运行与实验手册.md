## 6. GPU 使用规则

每次实验启动前都必须重新检查，而不能沿用上次结果：

```bash
nvidia-smi --query-gpu=index,name,memory.total,memory.used,memory.free,utilization.gpu \
  --format=csv,noheader

nvidia-smi --query-compute-apps=gpu_uuid,pid,process_name,used_memory \
  --format=csv,noheader
```

选择两张空闲或负载很低的 GPU：

- 不终止、修改或抢占其他用户进程；
- 优先选择剩余显存最多的两张卡；
- 两张卡建议各至少有约 12GB 可用显存；
- 若没有两张合适显卡，则不启动实验；
- 将启动前 GPU 状态写入日志。

两卡分工：

```text
物理 GPU A -> 逻辑 cuda:0 -> 冻结 Qwen
物理 GPU B -> 逻辑 cuda:1 -> Work2 可训练模块与冻结攻击模型
```

例如物理 GPU 3 和 1 空闲时：

```bash
CUDA_VISIBLE_DEVICES=3,1
```

配置文件中保持：

```json
{
  "backbone_device": "cuda:0",
  "trainable_device": "cuda:1",
  "target_device": "cuda:1"
}
```

### 8.2 正式主实验

正式配置固定使用第一工作点的 `batch_size=16`、训练期 `training_drop_last=true`、20 epoch、初始学习率 `0.01`、epoch 衰减 `0.8`，以及 `beta/alpha/gamma=1/3/0.9`。训练期间的验证只统计匹配正样本，不构造负样本；独立测试不丢弃尾批。

```bash
bash run_work2_deepcorr.sh
```

根据目标模型编辑 `vista_augur/configs/deepcorr_config.jsonc`、`vista_augur/configs/mdeepcorr_config.jsonc` 或 `vista_augur/configs/deepcoffea_config.jsonc`。三份文件均用明显分隔线划分日常运行、主要调参、目标协议和资源路径。启动器不检查 GPU 占用情况，会直接使用 `visible_gpu_devices` 中的序号。新实验需修改 `model_id`；断点训练将 `resume_from_checkpoint` 设为 `latest`。

正式测试命令：

```bash
# 在 JSONC 中设置：
# "run_mode": "evaluate"
# "resume_from_checkpoint": "best"
bash run_work2_deepcorr.sh
```

独立测试自动切换到 test 集，对每个正样本构造 199 个负样本，并分别为 clean 与 adversarial 结果校准 `10^-3`、`10^-4` FPR 阈值。负样本按 256 条分块送入冻结 DeepCorr，避免一次前向造成显存峰值。

## 9. Checkpoint 与恢复

输出目录格式为：

```text
vista_augur/outputs/checkpoints/<setting_name>/
```

其中包含：

- `generator_epNNN_origrecX_advrecX_lossX_timeX_sizeX.pt`：按 epoch 保存的完整恢复状态，文件名同时记录验证集原始 Recall、扰动后 Recall、损失、时间开销和大小开销；
- `latest.pt`：最近一次保存状态；
- `best.pt`：验证损失最低状态；
- 对应 JSON 摘要和 `train_summary.json`。

恢复训练：在统一 JSONC 中保持 `run_mode=train`，并将 `resume_from_checkpoint` 设为 `latest`，然后执行：

```bash
bash run_work2_deepcorr.sh
```

只评估 checkpoint：将 `run_mode` 设为 `evaluate`，将 `resume_from_checkpoint` 设为 `best`，然后仍执行：

```bash
bash run_work2_deepcorr.sh
```

## 10. 实验执行顺序

正式工作建议按以下顺序推进：

```text
单元测试
  -> DeepCorr300 正式主实验
  -> 时间/大小与模块消融
  -> m-DeepCorr、DeepCoFFEA 跨目标验证
  -> 低 FPR 评估与论文汇总
```

每一步都应满足：没有 OOM、NaN、数据错误或梯度中断，且输出摘要与 checkpoint 正常，再进入下一步。

## 11. 指标解释

| 指标 | 含义 |
| --- | --- |
| `original_positive_rate` | 原始匹配流量的检测率 |
| `adv_positive_rate` | 加入扰动后的检测率 |
| `attack_success_rate` | 原本被检测、扰动后未被检测的比例 |
| `time_ratio` | 时间扰动归一化 L2 开销 |
| `size_ratio` | 大小扰动归一化 L2 开销 |
| `clean_*`、`adv_*` | 基于正负配对计算的分类指标 |

正式测试沿用第一工作点的 1,000 条正样本和每条 199 个负样本，在 `10^-3`、`10^-4` FPR 下报告 PRE、REC 与 F1。训练日志中的固定阈值 `0.1` 只用于观察正样本 Recall，不作为论文正式表格结果。

## 12. 常见问题

### 12.1 找不到基模

确认以下文件存在：

```text
base_models/Qwen2.5-1.5B-Instruct/config.json
base_models/Qwen2.5-1.5B-Instruct/model.safetensors
```

远程服务器无法稳定访问 Hugging Face 时，应从本地同步完整快照，不要让训练过程临时联网下载。

### 12.2 找不到攻击模型权重

从仓库根目录运行，并检查配置中的 `target_model_path`。权重属于本地大文件，不会由 Git 自动拉取。

### 12.3 CUDA OOM

依次检查：

1. 是否选择了真正空闲的两张卡；
2. `CUDA_VISIBLE_DEVICES` 与配置中的逻辑卡号是否一致；
3. 是否误用了更大的旧基模；
4. 是否可以降低 `batch_size` 并提高梯度累积步数；
5. 是否有其他用户在实验启动后占用了同一张卡。

### 12.4 日志长时间没有输出

首次加载 DeepCorr pickle、Qwen 和大型攻击模型可能需要较长时间。先检查进程、内存和 GPU 状态，不要立即重复启动第二个任务。

### 12.5 DeepCoFFEA 使用 val 报错

当前会话文件提供 train/test，配置应使用：

```json
{"eval_split": "test"}
```
