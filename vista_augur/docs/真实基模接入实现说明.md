# 真实基模接入实现说明

## 1. 这次实现完成了什么

这次代码修改完成了两件本质上不同、但必须一起做的工作：

1. 把第二工作点的主训练链路固定到真实 `torch_real` 路径。
2. 把早期 stub 结构彻底移除，避免后续继续维护双轨实现。

所以最终结果不是“又多了一条 real 分支”，而是“仓库里只剩下真实主线”。

## 2. 代码层面的关键变化

### 2.1 训练入口收敛

- [run_train.py](/home/nixilin/work2/vista_augur/run_train.py) 现在是唯一训练入口
- `run_train_stub.py` 已删除
- 默认配置改为 `DeepCorr300 + text_prototypes` smoke

这意味着从入口层开始，代码心智模型就不再有“stub 还是 real”的二选一。

### 2.2 配置层收敛

[config.py](/home/nixilin/work2/vista_augur/second_workpoint/config.py) 做了三类调整：

- 默认值改成真实路径：`torch_real / real / hf_frozen / torch`
- 删掉只服务于 stub 的字段，例如哈希 prompt 和 stub dataset 的相关配置
- 把原来的“允许两种后端”的校验改成“只允许真实主线”

这样带来的直接效果是：任何旧的 stub 配置都会在加载阶段被拒绝，而不会拖到运行期才暴露问题。

### 2.3 数据层收敛

数据相关改动集中在：

- [factory.py](/home/nixilin/work2/vista_augur/second_workpoint/data/factory.py)
- [preprocessing.py](/home/nixilin/work2/vista_augur/second_workpoint/data/preprocessing.py)
- [__init__.py](/home/nixilin/work2/vista_augur/second_workpoint/data/__init__.py)

核心变化有两个：

- `StubFlowDataset` 已删除
- 真实样本接口不再生成 `prompt_ids`，只保留 `prompt_text`

这个改动很重要，因为它把“真实语义对齐的主输入到底是什么”这件事彻底钉死了。

### 2.4 模型层收敛

模型子包现在只导出：

- [FrozenQwenBackbone](/home/nixilin/work2/vista_augur/second_workpoint/models/qwen_backbone.py)
- [SecondWorkpointTorchRealModel](/home/nixilin/work2/vista_augur/second_workpoint/models/torch_real_model.py)

被删除的 stub 文件包括：

- `backbone_stub.py`
- `second_workpoint_model.py`
- `target_model_stub.py`

同时，`SecondWorkpointTorchRealModel.forward()` 现在只接受：

- `history_seq`
- `prompt_text`

不再保留任何 `prompt_ids` 兼容参数。

### 2.5 target model 适配层收敛

[target_model_adapter.py](/home/nixilin/work2/vista_augur/second_workpoint/models/target_model_adapter.py) 现在只保留真实 torch target model 路径。

这一步的意义不是“删掉一个备用实现”这么简单，而是：

- target 反馈正式成为真实训练链路的一部分
- 代码语义里不再存在“假 target”和“真 target”并存的状态

### 2.6 trainer 收敛

[trainer.py](/home/nixilin/work2/vista_augur/second_workpoint/training/trainer.py) 现在只保留 `TorchTrainer`。

被清掉的旧分支包括：

- `StubTrainer`
- 伪梯度构造
- `apply_stub_update`
- `npz` 风格的 stub checkpoint

当前 trainer 的唯一职责是：

- 组装真实 dataloader
- 运行真实前向
- 调用真实 loss
- 依赖 autograd 训练可学习模块
- 保存 trainable state 和 optimizer state

## 4. 语义对齐实现如何保留下来

这次去 stub 没有削弱语义对齐实验面，反而把它整理得更干净。

当前仍然保留两种实现：

| 模式 | 作用 |
| --- | --- |
| `text_prototypes` | 默认主方案，贴近 Time-LLM |
| `learned_prototypes` | 对照方案，保留做消融 |

因为 stub 已经删除，这两个模式现在都运行在同一条真实训练主线上，比较结果会更干净。

## 5. 为什么这更利于后续上更大基模

去掉 stub 后，后续扩展时需要考虑的变量变少了。

以前你要同时想：

- real 路径怎么改
- stub 是否还要跟着兼容

现在你只需要想：

- backbone 从 `3B` 升到 `7B` 怎么调
- batch / accumulation 怎么设
- quantization 是否要调整
- target 反馈实验怎么放大

这会明显降低后续训练工程的维护成本。

## 6. 当前代码修改后的心智模型

可以用下面这张图来理解当前第二工作点：

```mermaid
flowchart LR
    A[Real Dataset] --> B[prompt_text + history_seq]
    B --> C[Trainable Adapters]
    C --> D[Semantic Alignment]
    D --> E[Width Bridge]
    E --> F[Frozen Qwen]
    F --> G[Perturbation Head]
    G --> H[adv_flow]
    H --> I[Frozen Target Model]
    I --> J[TargetedOverheadLoss]
    J --> K[Backward to Trainable Modules]
```

这个结构现在既是 bring-up 用的最小链路，也是未来正式训练的缩小版。
