# Git Ignore 说明

## 这份 `.gitignore` 解决什么问题

这份规则文件的目标不是“尽量多忽略”，而是划清一个稳定边界：

- 保留应进入版本控制的内容，例如源码、配置、实验方案和正式说明文档。
- 排除只在本机有意义、体积大、可再生成、或者会污染提交记录的内容，例如数据集、模型权重、缓存和本地运行状态。

因为这个仓库是 Augur 研究工作区，很多文件同时具有“实验价值”和“运行产物”两种属性，所以忽略策略采用了 **按类别收敛**，而不是直接粗暴忽略整个模块目录。

## 当前被排除的内容

| 类别 | 规则示例 | 说明 |
| --- | --- | --- |
| OMX / Codex 本地状态 | `.omx/`, `.codex`, `.codex/` | 这些本地状态文件或目录保存会话状态、计划、日志和工具配置，不属于研究成果本体。 |
| 编辑器与系统杂项 | `.vscode/`, `Generator_Trainer/.vscode/`, `.idea/`, `.DS_Store` | 仅服务于个人开发环境，不应影响仓库内容。 |
| Python 缓存与虚拟环境 | `**/__pycache__/`, `*.py[cod]`, `.pytest_cache/`, `.venv/` | 可自动再生成，提交后只会制造噪声。 |
| 日志和临时文件 | `*.log`, `*.tmp`, `*.temp` | 一般用于本地调试或中间过程，不具备长期追踪价值。 |
| 本地数据集与基座模型 | `datasets/`, `base_models/` | 数据与基模型通常体积大、来源外部明确，适合本地挂载或单独管理，不直接进入 Git。 |
| Augur 主实现目录 | `Generator_Trainer/` | 当前按你的要求整体忽略，表示顶层仓库不再跟踪该目录中的源码、文档、数据和其内部元数据。 |
| 训练输出与检查点 | `work2/outputs/` | 包括训练摘要、checkpoint、导出权重等派生产物。 |
| 目标模型派生产物 | `target_model/**/*.pth`, `Generator_Trainer/target_model/**/*.npz` 等 | 针对权重、pickle、npz 这类本地生成或复制进来的二进制实验产物做排除。 |

## 明确不排除的内容

下面这些内容仍然应该纳入版本控制：

- `work2/second_workpoint/` 下的源码文件，例如 `.py`。
- `work2/configs/` 下的实验配置文件，例如 `.json`。
- `work2/docs/` 下的说明文档、方案文档和需要保留的研究记录。
- `target_model/` 中的代码文件本身；当前只排除了其中的二进制权重和数据产物，没有排除实现代码。

换句话说，这份规则默认针对“运行时派生物”和“本地大体量研究资产”；其中 `Generator_Trainer/` 现在被视为本地资产整体排除。

## 一条实用判断标准

如果一个文件满足下面任一条件，通常就应该被忽略：

- 可以通过脚本、训练或下载重新得到。
- 只对当前机器或当前会话有意义。
- 体积很大，但不承载源码级决策信息。
- 提交后难以做代码审查，也不利于版本比较。

如果一个文件承载的是：

- 算法实现
- 实验配置
- 研究结论
- 方法说明
- 可复现流程定义

那它通常不应被 `.gitignore` 排除。

## 后续维护建议

- 如果后面新增新的输出目录，例如 `results/`、`runs/`、`cache/`，建议按目录名追加规则，而不是扩大为全局通配，避免误伤真实资料。
- 如果某些二进制文件需要被正式版本化，例如小型样例数据或固定基准权重，建议单独做白名单，而不要直接删掉现有忽略边界。
- 在执行首次提交前，可以先运行 `git status`，确认被跟踪的文件主要集中在源码、配置和文档三类。这样最稳妥。
