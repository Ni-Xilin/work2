# 真实基模接入与训练主线设计说明

## 1. 设计目标

第二工作点现在的设计目标已经不是“给未来真实训练预留接口”，而是：

- 直接把真实训练主线落在 `work2/second_workpoint/`
- 用最小 smoke 配置证明这条主线真实可跑
- 同时保持它后续可以平滑扩展到更大 backbone 与更大显存环境

因此，当前设计必须同时满足两类要求：

| 维度 | 要求 |
| --- | --- |
| 最小链路 | 在 `deepcorr` 环境中可运行、可验证 |
| 长期扩展 | 不因为当前是 bring-up 环境，就把架构写成一次性低配版本 |

## 2. 当前唯一保留的主路径

当前代码只保留一条训练主线：

`real dataset -> trainable adapters -> semantic alignment -> frozen Qwen -> perturbation head -> frozen target -> loss`

对应的实现约束是：

- `backend=torch_real`
- `data_loader=real`
- `backbone_mode=hf_frozen`
- `target_model_mode=torch`

这四个字段仍然被保留在配置层，但它们现在不再是“多路选择器”，而是对唯一主路径的显式声明。

## 3. 为什么要彻底移除 stub

stub 在早期阶段有价值，是因为它能快速暴露模块边界问题。但现在继续保留它，会引入三个真实成本：

### 3.1 配置和代码入口会长期双轨化

只要 stub 还在，下面这些地方就必须一直做分支：

- config 校验
- dataset factory
- trainer factory
- run entrypoint
- 文档与实验说明

这会让每次扩展 backbone、target 或数据集时都多出一次“是否还兼容 stub”的额外思考。

### 3.2 prompt 语义入口会持续模糊

如果同时保留 `prompt_text` 和哈希 `prompt_ids` 两套心智模型，那么后续任何关于“语义对齐”的讨论都会混入一个历史遗留问题：

- 到底是自然语言 prompt 在起作用
- 还是占位 token 接缝还没有真正拔掉

### 3.3 对未来更大 backbone 不利

后续你关心的是：

- `3B -> 7B`
- `2080 smoke -> 4090 train`
- 更长 prompt
- 更稳定的 target 反馈实验

这些扩展都属于真实主线内部的放大问题，而不是“再保留一个伪训练后端”能帮上忙的类别。

## 4. 基模接入的核心设计

### 4.1 tokenizer 与 prompt 必须是真实路径

当前主路径固定为：

`prompt_text -> tokenizer -> prompt embeddings -> inputs_embeds`

这是一个关键选择，因为它决定了 prompt 在架构里的角色是真正的语言锚点，而不是未来再替换的占位字段。

### 4.2 backbone 参数冻结，但前向仍保留在计算图里

这件事决定了 generator 侧是否真的在学习“如何影响真实基模隐藏状态”。

如果只做参数冻结：

- Qwen 自己不更新
- 上游 trainable token 仍能收到梯度

如果错误地再加上 `torch.no_grad()`：

- 梯度会在 backbone 处被彻底切断
- generator 实际上学不到任何依赖基模语义空间的内容

### 4.3 trainable width 必须稳定

当前 generator 侧不直接绑死在 backbone hidden size 上，而是维持一个稳定的 `trainable_width`，再通过 `BackboneWidthBridge` 进入基模 embedding width。

这个选择的意义在于：

- `3B` 和 `7B` 的切换不必重写 generator 主体
- bring-up 阶段和正式训练阶段共享同一结构
- 语义对齐层的实验比较更公平

## 5. 语义对齐为什么做成双模式

当前支持：

- `text_prototypes`
- `learned_prototypes`

这里不是为了兼容旧代码，而是为了实验解释力。

### `text_prototypes`

- 更贴近 Time-LLM
- 直接使用冻结基模的 embedding 矩阵作为语义原型来源
- 更适合作为主论文式方案

### `learned_prototypes`

- 原型本身是自由学习的参数
- 语言先验更弱
- 适合作为消融基线

## 6. 当前设备拓扑为什么这样安排

默认拆分是：

- `cuda:0`：frozen Qwen backbone
- `cuda:1`：trainable modules + frozen target model

这个拆分并不是为了 2080 特化，而是因为它对后续更大显存环境仍然成立：

- backbone 的主要压力是权重与前向激活
- target 与扰动写回逻辑强耦合，和 trainable stack 放同卡更直观

后面切到 `4090 24GB`，你更可能做的是：

- 把同样的拓扑搬过去
- 增大 batch
- 提升 backbone 规模

而不是改训练主线的边界。

## 7. 当前设计已经锁定的 ABI

为了避免后面再次大改，当前主线已经默认以下 ABI：

| 位置 | 当前 ABI |
| --- | --- |
| prompt 输入 | `prompt_text: list[str]` |
| generator 输入 | `history_seq: torch.Tensor` |
| backbone 接缝 | `inputs_embeds` |
| 语义对齐主模式 | `text_prototypes` |
| 目标反馈 | 真实 torch target model |
| checkpoint | 只保存 trainable state + optimizer state |

## 8. 下一阶段应该关注什么

这条设计线已经回答了“最小真实链路怎样建”。下一阶段更值得关心的是：

1. `4090 24GB` 下的正式训练 profile 怎么设。
2. `3B` 与 `7B` 在 `text_prototypes` 模式下的差异如何衡量。
3. DeepCorr 与 DeepCoFFEA 是否需要不同的 batch / accumulation 默认值。
4. 是否要把 prototypes 的选择策略再扩展成更细粒度的可配置实验面。
