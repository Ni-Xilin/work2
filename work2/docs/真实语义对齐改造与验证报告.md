## 1. 背景与问题

在这次改造之前，第二工作点的真实 `torch_real` 主线虽然已经能跑真实 `prompt_text -> tokenizer -> inputs_embeds -> frozen Qwen`，但语义对齐层仍然沿用了“自由可学习 prototype 矩阵”的写法。这个实现能训练，也能跑 smoke，但它和 Time-LLM 论文中的语义对齐机制并不完全一致。

论文同款机制强调的不是“有一组 prototype”这么简单，而是：

- prototype bank 需要来自冻结 backbone 的预训练词表 embedding 空间，而不是一张完全脱离语言先验的自由参数表
- 更具体地说，是先拿到 backbone 的 input embedding 矩阵 `E \in \mathbb{R}^{V \times D}`
- 再通过一个小型可学习矩阵 `W \in \mathbb{R}^{V' \times V}` 构造 `E' = W E`
- 最后让 patch token 以 query 身份对 `E'` 做 multi-head cross-attention

如果不把这一步改正，文档里虽然可以继续说“有 reprogramming”，但严格来说，这仍然更接近“自由语义字典”，而不是论文同款的 `text prototypes`。

---

## 2. 两种模式总览

### 2.1 一张表先看清

| 模式 | 配置值 | 当前定位 | prototype 来源 | 路由方式 | 是否保留 |
| --- | --- | --- | --- | --- | --- |
| 论文同款模式 | `text_prototypes` | 默认推荐主线 | `E' = W E` | multi-head cross-attention | 是 |
| 回退/消融模式 | `learned_prototypes` | 对照与回归 | 自由原型矩阵 `P` | 相似度 + softmax + 原型重组 | 是 |

### 2.2 为什么两种都保留

- `text_prototypes` 是现在真正应该拿来继续做实验和扩展 backbone 的主线，因为它和论文语义对齐定义一致。
- `learned_prototypes` 不能直接删掉，因为后面做消融时，很可能要比较“语言先验带来的收益”和“仅仅有一层轻量重编程是否已经足够”。
- 从工程角度看，保留两种模式还能证明这次改造不是“把旧实现推倒重写”，而是在相同训练 ABI 下替换语义对齐内核。

## 3. `text_prototypes` 实现细节

这一节回答：代码里到底怎样把论文机制落下来。

### 3.1 数学主线

论文同款语义对齐现在按下面的形式落地：

$$
E \in \mathbb{R}^{V \times D}
$$

$$
W \in \mathbb{R}^{V' \times V},\qquad E' = W E,\qquad V' \ll V
$$

对于任意一条非文本 token 序列 `\hat{H} \in \mathbb{R}^{B \times P \times d_m}`，分别构造：

$$
Q = \hat{H} W^Q,\qquad K = E' W^K,\qquad V = E' W^V
$$

再通过 multi-head cross-attention 得到：

$$
Z = \operatorname{MHA}(Q, K, V)
$$

最后再通过 width bridge 投到 backbone embedding 宽度，送入冻结 Qwen。

### 3.2 为什么不把整张词表 embedding 常驻复制到训练卡

如果只为了当前 `3B` smoke 去设计，最简单的方法是把 `E` 整张表直接复制到 `trainable_device`。但这会带来一个明显问题：

- 当前 `3B` 也许还能勉强接受
- 后续如果切到更大的 backbone，例如 `7B` 或更高维度的 embedding，这个复制策略会持续蚕食训练卡显存

所以这次实现刻意采用了更利于扩展的路径：

- `E` 保持留在 `backbone_device`
- `W` 保持是训练卡上的可学习参数
- 每次前向时，只在 backbone 卡上计算小型 `E' = W E`
- 再把尺寸已经大幅压缩后的 `E'` 送回训练卡，供 cross-attention 使用

这个决定的意义在于：以后 backbone 放大时，训练卡承受的不是整张词表 embedding，而只是 `V' \times D` 这一小块 prototype bank。

### 3.3 和 prompt 的关系

`text_prototypes` 只解决“非文本模态如何进入语言 embedding 空间”这个问题；它不替代 prompt，也不把 prompt 当作主要对齐对象。

现在真实主线中，prompt 的职责仍然是：

- 作为天然语言锚点进入 tokenizer
- 通过 `inputs_embeds` 和重编程后的 time/visual token 一起送入冻结 Qwen
- 为 backbone 提供任务语境和语言参照系

换句话说：

- prompt 是语言空间中的锚点
- `text_prototypes` 是非文本模态通往语言空间的桥

这两者不是竞争关系，而是职责分工关系。

## 4. `learned_prototypes` 还剩下什么价值

`learned_prototypes` 并不是“错的实现”，而是“语义先验更弱的实现”。

它现在仍然有三个价值：

- 作为回归开关，可以快速判断新问题究竟出在 `text_prototypes` 逻辑，还是出在更外围的 trainer / target / writeback 链路。
- 作为消融基线，可以回答“收益来自论文同款语言 prototype，还是来自任何一种轻量重编程层”。
- 作为低复杂度对照，可以帮助解释未来实验中 `text_prototypes` 的增益来源。

因此，这次改造不是删掉 `learned_prototypes`，而是把它从“唯一实现”降级为“可选对照模式”。

## 7. 面向更大基模的设计含义

这次实现最重要的长期价值，不是“在 2080 上也能勉强跑”，而是它已经尽量避免了以后放大 backbone 时会迫使你再重构一次的几个典型坑。

### 7.1 trainable width 和 backbone width 继续解耦

- generator 侧仍然保持稳定的 `trainable_width`
- backbone 的真实 embedding 宽度由具体 Qwen 模型决定
- 两者之间继续通过 `BackboneWidthBridge` 对接

这意味着以后从 `3B` 切到 `7B`，最核心的形状变化仍然被限制在 bridge 与 backbone 交界面，而不是反向传染到所有 trainable 模块。

### 7.2 语义对齐不再依赖自由 `P` 才能成立

使用 `text_prototypes` 之后，prototype bank 已经天然落在 backbone 的预训练 embedding 空间里。这会带来两个现实好处：

- 语义解释更自然，因为 prototype 来源于语言词表 embedding
- 后续如果要比较不同 backbone，语义对齐层的定义也更稳定

### 7.3 prompt 长度控制和 stub 哈希长度彻底分离

过去最大的一个隐患是：

- `prompt_len` 同时被当作 stub 哈希长度和真实 tokenizer 上限

这会让真实训练路径背上一个本来属于 stub 的历史包袱。现在把它拆成：

- `prompt_len`：仅 stub 使用
- `backbone_prompt_max_tokens`：真实 tokenizer 使用

这样后续不管改 prompt 模板、换 backbone，接口都更清楚。

## 8. 当前结论

可以把这次结果压成三句话：

- 第二工作点真实主线已经从“自由原型的可训练 reprogramming”升级成了“与 Time-LLM 一致的 `text prototypes` 语义对齐”。
- 这次升级不是为了当前 smoke 特化，而是专门按以后扩展到更大 backbone 仍然成立的接口去设计的。
- 现在两条模式都已经有真实 smoke 证据，因此后续训练与消融都可以直接在这套代码上继续展开。
